# midilib audit — MIDI 1.0 spec adherence

**Date:** 2026.06.17
**Project root:** `/Users/oubiwann/lab/erlsci/midilib`
**Dimension covered:** (3) adherence to the authoritative MIDI 1.0 specifications in `priv/docs/`.
**Citation rule:** every finding cites the governing PDF and a section/page; an uncited claim has been moved to the erlang (conceptual-correctness) report instead. MIDI 2.0 / UMP and Bit-Scaling PDFs are out of scope (midilib is a 1.0 library); the only 2.0 concern would be 1.0/2.0 conflation, of which none was found.

**Spec corpus referenced (in `priv/docs/`):**
- **Detailed Spec** — `MIDI 1.0 - Spec (M1_v4-2-1_MIDI_1-0_Detailed_Specification_96-1-4).pdf`
- **SMF** — `MIDI 1.0 - Files (RP-001_v1-0_Standard_MIDI_Files_Specification_96-1-4).pdf`
- **Time Code** — `MIDI 1.0 - Time Code (RP-004-008_v4-2-1_MIDI_Time_Code_Specification_96-1-4).pdf`

## Executive summary

Measured against the spec PDFs, midilib's *wire* codec (`midibin`) is largely faithful — status nibbles, the 14-bit fields, channel numbering, MTC quarter-frame layout, and the real-time byte values all match the Detailed Spec tables. The *file* codec (`midifile`) is where spec adherence breaks down: SysEx events are framed incorrectly on read (the `F0` byte is unaccounted, RP-001 p.6), the Sequence/Track-Name meta-event is written with the End-of-Track type byte (RP-001 pp.8-10), Sequencer-Specific events are mis-tagged, and `write/2` emits a hardcoded format-1 header regardless of the file's real format (RP-001 pp.4-5). One non-file finding is purely spec-driven: `midimsg:rt_tick/0` invents a System Real-Time "tick" that the Detailed Spec marks Undefined. **There is no architecture/design document in the repo**, so none of these encodings could be checked against a stated intent — only against the specs themselves. Severities here mirror the wire/file impact; the same defects appear with code-level fixes in the erlang report.

## Correctness / soundness (spec violations)

### S1. SysEx is restricted to a single 7-bit byte; the spec defines it as arbitrary-length  — **Blocker**
**Location:** `src/midibin.erl:137-138` (decode), `:410-411` (encode)
**Governing spec:** Detailed Spec, **Table VII, p. T-8**: *"F0H … Any number of data bytes may be sent here, for any purpose, as long as they all have a zero in the most significant bit … F7H … EOX: End of System Exclusive."* Also Detailed Spec p. 4: *"Exclusive messages can contain any number of Data bytes, and can be terminated either by an End of Exclusive (EOX) or any other Status byte (except Real Time messages)."* SMF, **p. 6**: a complete SysEx is stored `F0 <length> <bytes…>` and *"It is required to include the F7 at the end."*
**What's wrong:** The codec models the entire SysEx payload as one 7-bit integer `<<…, Data:7>>`, with no `F7` terminator in the pattern at all.
**Why it's wrong:** A spec-legal SysEx of any length other than one byte cannot be represented or encoded (encode of a binary payload throws `badarg`; decode of `F0 … F7` falls through to `{unknown, Bin}`). midilib cannot interoperate with any device-format SysEx. Cross-ref erlang report #8, consumer report §C1.

### S2. `midifile` SysEx read mis-frames the event — the `F0` status byte is unaccounted  — **Blocker**
**Location:** `src/midifile.erl:193-199`
**Governing spec:** SMF, **p. 6**: *"A normal complete system exclusive message is stored in a MIDI File in this way: F0 <length> <bytes to be transmitted after F0>. The length is stored as a variable-length quantity… the transmitted message F0 43 12 00 07 F7 would be stored… as F0 05 43 12 00 07 F7."*
**What's wrong:** The reader takes the VLQ length at `FilePos + 1` correctly, but reads the payload at `FilePos + LengthBytesUsed` (should be `FilePos + 1 + LengthBytesUsed`) and reports `LengthBytesUsed + Length` bytes consumed (should be `1 + LengthBytesUsed + Length`). The single `F0` byte at `FilePos` is never counted — contrast the meta-event reader at `:152-155`, which correctly accounts for its two prefix bytes.
**Why it's wrong:** Per the spec layout `F0 <vlq-length> <data…F7>`, the data begins one byte after where the code reads it, and the event's true on-disk size is one byte larger than reported. The track byte-counter (`event_list/4`, `:81-91`) consequently desynchronises and the remaining track is parsed from a corrupt offset. Cross-ref erlang report #1.

### S3. Sequence/Track-Name meta-event is written with the End-of-Track type byte  — **Blocker**
**Location:** `src/midifile.erl:319-321`
**Governing spec:** SMF, **Meta-Events, pp. 8-10**: *"FF 03 len text — Sequence/Track Name"* and *"FF 2F 00 — End of Track … This event is not optional … length 0."*
**What's wrong:** `event_io_list({seq_name, …})` writes type `?META_TRACK_END` (`0x2F`) instead of `?META_SEQ_NAME` (`0x03`).
**Why it's wrong:** The serialised byte sequence is no longer a name event — a conforming reader interprets `FF 2F` as End-of-Track and stops reading the track. Output violates the meta-event table and truncates the track. Cross-ref erlang report #2.

### S4. Sequencer-Specific meta-events (`0x7F`) are read as Sequence/Track-Name  — **High**
**Location:** `src/midifile.erl:187-188`
**Governing spec:** SMF, **pp. 8-10**: *"FF 7F len data — Sequencer-Specific Meta-Event"* is a distinct type from *"FF 03 len text — Sequence/Track Name."*
**What's wrong:** `?META_SEQUENCER_SPECIFIC` is tagged `{seq_name, …}`, the same tag used for the real `0x03` name event (`:165-166`).
**Why it's wrong:** Two spec-distinct meta types collapse to one tag, so the type information mandated by the spec table is lost on read, and the (already broken) `seq_name` write path then re-emits both as `0x2F`. Cross-ref erlang report #4.

### S5. `write/2` always emits a format-1 header word, ignoring the file's real format  — **High**
**Location:** `src/midifile.erl:243-251` (constant `0, 1` at `:246`); `read/1` parses the real format at `:51-53`.
**Governing spec:** SMF, **Header Chunk, pp. 4-5**: *"0 the file contains a single multi-channel track; 1 … one or more simultaneous tracks …; 2 … one or more sequentially independent single-track patterns,"* and *"<ntrks> … will always be 1 for a format 0 file."*
**What's wrong:** The parsed `Format` (preserved in `Header = {header, Format, Division}`) is discarded; `header_io_list/2` hardcodes the format word to `0, 1` and always writes `length(Tracks) + 1` tracks.
**Why it's wrong:** A format-0 or format-2 file round-tripped through this module is rewritten with a false format declaration (and, for format 0, an invalid multi-track count), contradicting the header the spec defines. Cross-ref erlang report #6.

### S6. `rt_tick/0` invents a System Real-Time message the spec marks Undefined  — **Medium**
**Location:** `src/midimsg.erl:296-298`
**Governing spec:** Detailed Spec, **Table VI, p. T-7**: System Real-Time bytes are *"F8H Timing Clock; F9H Undefined; FAH Start; FBH Continue; FCH Stop; FDH Undefined; FEH Active Sensing; FFH System Reset."* The only two free real-time slots (`F9`, `FD`) are explicitly Undefined; p. A-2 adds they *"should always be ignored."*
**What's wrong:** `rt_tick/0` returns `{midi, {realtime, tick}}` — there is no "tick" real-time message in the spec.
**Why it's wrong:** A public constructor names a message that does not exist on the wire; `midibin` rightly has no encoding for it (it falls to `ERR_MIDI_UNSUP`). Cross-ref erlang report #9, consumer report §C6.

### S7. `read_var_len` accepts a 4-byte VLQ with no terminator byte  — **Medium**
**Location:** `src/midifile.erl:223-225` (the fifth clause)
**Governing spec:** SMF, **Conventions, p. 2**: *"All bytes except the last have bit 7 set, and the last byte has bit 7 clear … The largest number which is allowed is 0FFFFFFF so that the variable-length representation must fit in 32 bits."*
**What's wrong:** The final clause matches `<<1:1,B0:7, 1:1,B1:7, 1:1,B2:7, 1:1,B3:7>>` — *all four* high bits set, i.e. no terminating byte — and returns a value anyway (with only a `?DPRINT` warning).
**Why it's wrong:** Such a byte sequence is not a valid VLQ (the spec requires bit 7 clear on the last byte); silently accepting it masks a malformed file and yields a number whose continuation was never terminated. The writer side (`var_len/1`, `:373-382`) correctly enforces the `0x0FFFFFFF`/28-bit ceiling, so the read side is the asymmetry. (The writer's overflow *handler* is itself buggy — erlang report #5 — but its ceiling matches the spec.)
**Fix:** treat the all-high-bits case as `{error, {bad_vlq, …}}` rather than a value.

### S8. Note-On velocity 0 is correctly treated as Note-Off, but read invents a release velocity  — **Low** (conceptual; spec confirms only the equivalence)
**Location:** `src/midifile.erl:100-105`
**Governing spec:** Detailed Spec, **p. 10** and **Table II, p. T-2**: *"a note may be turned off … by sending a Note-On message for that note and channel with a velocity value of zero,"* and `9nH … vvvvvvv = 0: note off`.
**What's wrong / why:** The *equivalence* the code applies (Note-On vel 0 ⇒ Note-Off) is spec-correct. What the spec does **not** sanction is substituting a release velocity of `64` (`[Chan, Note, 64]`): the original event carried no release velocity, and 64 is an invention that then drives the lossy write path. This is recorded here only as a spec boundary note; the data-loss mechanism and fix are in erlang report #7.

## Things I looked for and did not find (clean checks)

1. **Channel numbering matches the spec.** `midibin` maps the status nibble to human channel numbers with `Channel + 1` / `Channel - 1` (`midibin.erl:16,169` et al.), exactly the Detailed Spec **Table I, p. T-1** rule: *"nnnn: N-1, where N = Channel #, i.e. 0000 is Channel 1 … 1111 is Channel 16."* (The *internal* `midibin`-vs-`midifile` base mismatch is a family-consistency issue, not a spec violation — consumer report §C7.)
2. **Pitch-Bend resolution and byte order are spec-correct.** `midibin.erl:38-40` decodes `0:1,Lsb:7,0:1,Msb:7` → `(Msb bsl 7) + Lsb`, matching Detailed Spec **Table II, p. T-2** (LSB first, then MSB) and **p. 25** (14-bit, centre `00H, 40H` = `0x2000`). Encode (`:205-215`) reproduces the same order.
3. **Song Position Pointer is 14-bit, LSB-then-MSB.** `midibin.erl:99-100,366-372` matches Detailed Spec **Table V, p. T-6**: *"F2H … 0lllllll: (Least significant) 0hhhhhhh: (Most significant)."*
4. **MTC Quarter Frame layout is correct.** `midibin.erl:96-97,361-362` encodes/decodes `F1` with a 3-bit message type and 4-bit value (`0:1, MessageType:3, Value:4`), matching the Time Code spec **p. 1** (*"a nibble that represents the message type (0 through 7), and a nibble for one of the digits of a time field"*) and Detailed Spec **Table V, p. T-6** (`0nnndddd`).
5. **System Real-Time byte values are all correct.** `midibin.erl:115-131,393-404`: `F8` clock, `FA` start, `FB` continue, `FC` stop, `FE` active sensing, `FF` reset — verbatim Detailed Spec **Table VI, p. T-7**. The undefined `F9`/`FD` are (correctly) absent.
6. **The dual meaning of `0xFF` is handled correctly per context.** On the wire `midibin` decodes a lone `255` as `{realtime, reset}` (`:130-131`) — System Reset, Detailed Spec Table VI; in a file `midifile` treats `0xFF` as the meta-event prefix (`?STATUS_META_EVENT`, `include/midi.hrl:32`, `midifile.erl:148`) — SMF p. 7 (*"All meta-events begin with FF"*). No conflation between the two paths.
7. **Set Tempo is parsed as 24-bit microseconds-per-quarter-note.** `midifile.erl:177-180` reads three bytes into `(B0 bsl 16) + (B1 bsl 8) + B2`, and the writer (`:332-338`) emits three bytes with `var_len(3)` length — matching SMF **p. 9** (*"FF 51 03 tttttt — Set Tempo, in microseconds per MIDI quarter-note"*).
8. **VLQ *writer* honours the spec ceiling.** `var_len/1` (`midifile.erl:373-381`) encodes 1–4 bytes for values `< 1 bsl 28`, matching SMF **p. 2** (max `0x0FFFFFFF`). (Only its overflow *handler* is broken — erlang report #5 — and only the *reader*'s 5th clause is too permissive — S7.)
9. **End-of-Track is read with the correct type byte and zero length.** `midifile.erl:142-147` matches `<<?STATUS_META_EVENT:8, ?META_TRACK_END:8, 0:8>>` = `FF 2F 00`, per SMF **pp. 8-10**. (The *write* side mis-emits it — that's a shape mismatch, S3/erlang #3, not a wrong type byte on read.)
