# midilib audit — Erlang practice & conceptual correctness

**Date:** 2026.06.17
**Project root:** `/Users/oubiwann/lab/erlsci/midilib`
**Branch:** `release/0.5.x` (HEAD `54fdf1a`)
**Dimensions covered:** (1) code quality & Erlang best practice, (2) conceptual MIDI correctness.
**Contract:** the erlang-guidelines guides (pattern IDs cited inline, e.g. `PC-12`, `EH-12`, `FP-12`). Spec-citation findings live in the companion `*-midi-spec.md`; consumer-API findings in `*-consumer-fit.md`; cross-references are noted.

## Executive summary

midilib is a pure four-module MIDI codec (`midibin` term⇄binary, `midifile` SMF read/write, `midimsg` constructors, `midiutil` helpers). **There is no architecture or design document in the repository** (closest are the downstream `midi`/`midiio` workbench bootstraps, which are not midilib design docs); intent had to be reconstructed from source, so several findings below concern invariants that were never written down. The codebase is sharply bimodal: `midibin` is clean, well-shaped, and the only module with tests, while `midifile` (inherited from Jim Menard's 2010 midilib) is defect-dense — its SMF reader desynchronises on the first SysEx event, two of its meta-event clauses emit or tag the wrong type byte, and `track_end` cannot survive a read→write round-trip. Two root-cause clusters dominate: (a) `midifile`'s reliance on **mutable process-dictionary state** for the running-status machine (`PC-12`), and (b) **three incompatible message vocabularies** across the modules despite `midimsg.erl:11-16` claiming a single "lingua franca." The compiler and the `midibin`-only test suite pass; that is evidence only that those two checks are satisfied — essentially none of `midifile`'s defects are exercised by a test.

## Correctness / soundness

### 1. `midifile` SysEx read is off-by-one — desynchronises the rest of the track  — **Blocker**
**Location:** `src/midifile.erl:193-199`
**What's wrong:** The clause matches `<<?STATUS_SYSEX:8, _:16>>` at `FilePos` (the `F0` byte). It reads the VLQ length at `FilePos + 1` (correct), but then reads the payload at `FilePos + LengthBytesUsed` and reports `LengthBytesUsed + Length` bytes consumed. Both omit the one byte occupied by the `F0` status byte: the payload should start at `FilePos + 1 + LengthBytesUsed`, and consumption should be `1 + LengthBytesUsed + Length`. Compare the meta clause at `:152-155`, which correctly uses `FilePos + 2` and `LengthBeforeData = LengthBytesUsed + 2` to account for the `FF` + type bytes.
**Why it's wrong:** The payload is read starting one byte early (overlapping the final length byte), and the running byte count handed back to `event_list/4` (`:88-91`) is one short. `event_list` decrements `BytesToRead` by that count and only terminates on an exact `0` (`:81`); once the count is wrong the remaining track is parsed from a shifted offset, `BytesToRead` can skip past `0` into negative territory (no guard clause matches), and parsing runs off the end of the track until `file:pread` returns `eof` and the `{ok, ThreeBytes}` match at `:85` fails with `badmatch`. Any SMF containing a single SysEx event is unreadable. Cross-ref spec report §2.
**Fix:** at `:198` read `file:pread(F, FilePos + 1 + LengthBytesUsed, Length)` and return `[{sysex, DeltaTime, [Data]}, 1 + LengthBytesUsed + Length]`.

### 2. `seq_name` is written with the End-of-Track type byte  — **Blocker**
**Location:** `src/midifile.erl:319-321`
**What's wrong:** `event_io_list({seq_name, …})` calls `meta_io_list(DeltaTime, ?META_TRACK_END, Data)` — type byte `0x2F` — where it must use `?META_SEQ_NAME` (`0x03`).
**Why it's wrong:** Every track whose name is serialised gets a spurious End-of-Track meta-event in place of the name; a reader hitting `0x2F` mid-track stops reading that track. The file is corrupt and truncated. Cross-ref spec report §3.
**Fix:** `meta_io_list(DeltaTime, ?META_SEQ_NAME, Data)`.

### 3. `track_end` read and write shapes disagree — round-trip crashes  — **Blocker**
**Location:** read `src/midifile.erl:147` emits `{track_end, DeltaTime, []}` (3-tuple); write `src/midifile.erl:309` matches `{track_end, DeltaTime}` (2-tuple).
**What's wrong:** `read/1` produces a 3-tuple for end-of-track, but `event_io_list/1` has no 3-tuple clause for it — only the 2-tuple at `:309`.
**Why it's wrong:** `read/1 → write/2` is the headline use case (the README advertises read and write). Feeding a track read from disk straight back to `write/2` raises `function_clause` on the `{track_end, DeltaTime, []}` event. Since `read/1` *always* appends a track-end, **no file read by this module can be written back out.**
**Fix:** change `:309` to `event_io_list({track_end, DeltaTime, _}) ->` (or `{track_end, DeltaTime, []}`), keeping the 3-tuple as the canonical shape.

### 4. Sequencer-Specific meta-events are read as `seq_name`  — **High**
**Location:** `src/midifile.erl:187-188`
**What's wrong:** `?META_SEQUENCER_SPECIFIC` (`0x7F`) is tagged `{seq_name, DeltaTime, [Data]}` — colliding with the real Sequence/Track-Name event (`0x03`) read at `:165-166` as `{seq_name, DeltaTime, binary_to_list(Data)}`.
**Why it's wrong:** Two distinct event types now share one tag with two *different* payload shapes (a wrapped binary `[Data]` vs. a char list). Downstream code cannot tell a track name from sequencer-specific bytes, and on write the `seq_name` clause (`:319`, itself buggy — see #2) mangles both. Cross-ref spec report §4.
**Fix:** `?META_SEQUENCER_SPECIFIC -> [{sequencer_specific, DeltaTime, [Data]}, TotalLength];` — which also matches the existing write clause at `:345`.

### 5. VLQ overflow handler crashes with `badarg`, not the intended message  — **High**
**Location:** `src/midifile.erl:381-382`
**What's wrong:** `exit("Value " ++ I ++ " is too big for a variable length number")` concatenates an **integer** `I` with `++`, which requires a list on both sides.
**Why it's wrong:** The guard path meant to report "delta-time too large for a VLQ" instead raises `badarg` inside `++`, so the diagnostic is never produced — the failure mode is a confusing arithmetic crash. Separately, signalling a library error via `exit/1` on a string violates `EH-02`/`EH-12` (see Error handling §). Cross-ref spec report §7 (the 28-bit ceiling itself is correct).
**Fix:** `exit({value_too_large_for_vlq, I})` — a structured, matchable reason that also avoids the `++` bug.

### 6. `write/2` hardcodes format 1 and discards the parsed format  — **High**
**Location:** `src/midifile.erl:243-251` (the literal `0, 1` at `:246`), against `read/1`/`parse_header` at `:51-53`.
**What's wrong:** `read/1` parses the real format into `Header = {header, Format, Division}`, but `header_io_list/2` destructures only `Division` (`:244`) and emits a constant `0, 1` format word; `Format` is thrown away. `NumTracks` is also always written as `length(Tracks) + 1` (`:239`), assuming the conductor-plus-N-tracks layout of format 1.
**Why it's wrong:** A format-0 (single multi-channel track) or format-2 file read by this module is silently rewritten as format 1, changing the file's declared type. The seed analysis said "the `seq` shape has no slot for the original format" — that is **inaccurate**: the format *is* preserved in `Header`; `write/2` simply ignores it. Cross-ref spec report §5; README at `README.md:39` advertises only "type 1."
**Fix:** at `:244` bind `{header, Format, Division} = Header` and emit `(Format bsr 8) band 255, Format band 255` in place of `0, 1`.

### 7. Note-off velocity is destroyed on write; note-on-vel-0 is reconstructed lossily on read  — **Medium**
**Location:** read `src/midifile.erl:100-105`; write `src/midifile.erl:276-291`
**What's wrong:** On read, a Note-On with velocity 0 is folded to `{off, DeltaTime, [Chan, Note, 64]}` — inventing a release velocity of 64. On write, `event_io_list({off, …})` takes the running-status branch whenever the channel matches and the running status is Note-Off *or* (Note-On with `Vel =:= 64`), and in that branch sets `OutVel = 0` unconditionally (`:283-284`). So a genuine Note-Off carrying a non-zero release velocity, emitted under running status `0x8n`, is written out with velocity 0.
**Why it's wrong:** Two distinct on-wire events (Note-Off vel V, and Note-On vel 0) are conflated into one internal `{off, …, [_, _, 64]}` representation, and the write path then forces velocity 0. Release velocity is lost, and the read↔write pair is only accidentally faithful for the vel-0 case. Note this fold is *normalization*, which the consumer layer explicitly owns (consumer report §C8) — the codec should be faithful. Cross-ref spec report §8.
**Fix:** preserve the real release velocity in the `off` tuple on read (don't substitute 64), and in the write branch emit `OutVel = Vel` (only the *status byte* should be elided under running status, never the data).

### 8. SysEx codec is single-7-bit-byte only; encoding a real SysEx binary crashes  — **Blocker**
**Location:** decode `src/midibin.erl:137-138`; encode `src/midibin.erl:410-411`; producer `src/midimsg.erl:304-306`
**What's wrong:** Both codec clauses model SysEx as exactly one 7-bit integer: `<<1:1, 7:3, 0:4, 0:1, Data:7>>`. `midimsg:sys_ex/1` is `-spec`'d to accept a `binary()`. Passing that binary to `encode/1` hits `<<… Data:7>>` with `Data` bound to a binary, which raises `badarg` at bit-syntax construction (a 7-bit segment requires an integer). A real inbound SysEx re-serialised as `<<0xF0, …, 0xF7>>` never matches `decode/1`'s one-byte clause and falls to the catch-all `{unknown, Bin}` (`:158-159`).
**Why it's wrong:** SysEx is arbitrary-length by definition (spec report §1); this is the single largest correctness gap and the family's #1 cross-layer blocker (consumer report §C1, `NEEDS-from-midiio.md` R7). The encode path is worse than incomplete — it throws.
**Fix:** model SysEx payload as a `binary()`: decode `<<16#F0, Rest/binary>>` splitting on the trailing `0xF7`; encode `{midi, {sys_ex, Bytes}}` as `<<16#F0, Bytes/binary, 16#F7>>`. Cross-ref spec report §1.

### 9. `rt_tick/0` constructs a message that does not exist and cannot be encoded  — **Medium**
**Location:** `src/midimsg.erl:296-298`
**What's wrong:** `rt_tick/0` returns `{midi, {realtime, tick}}`. There is no such System Real-Time message — the two free real-time status bytes `0xF9` and `0xFD` are *Undefined* in the spec — and `midibin:encode/1` has no clause for it, so it falls to `ERR_MIDI_UNSUP` (`midibin.erl:428-429`).
**Why it's wrong:** A public constructor produces a value that is meaningless on the wire and un-encodable by the project's own codec. Cross-ref spec report §6; consumer report §C6.
**Fix:** remove `rt_tick/0` and its `'rt-tick'/0` alias (`:352-353`, `:95`), or repoint it at Timing Clock (`0xF8`) if "tick" was intended as a clock alias — but document the choice.

### 10. `midiutil:quantize` arithmetic is dimensionally inconsistent and untested  — **Medium**
**Location:** `src/midiutil.erl:63-70`
**What's wrong:** `Diff = (BeatsFromStart + DeltaTime) div Boundary` is a *count of boundaries* (a quotient), yet it is compared against `Boundary / 2` (half a boundary, in time units) and then subtracted directly from `DeltaTime` (`DeltaTime - Diff`, `DeltaTime - Diff + Boundary`). Counts, half-boundaries, and delta-times are mixed without a consistent unit. Nearest-multiple quantisation should be `round(T / Boundary) * Boundary` with the new delta derived from the change in absolute position.
**Why it's wrong:** The result is not the nearest multiple of `Boundary` for general inputs; with no test (`midiutil` has none) the intended behaviour cannot even be pinned. This is a latent correctness bug hiding behind zero coverage.
**Fix:** recompute against absolute positions: `NewAbs = round((BeatsFromStart + DeltaTime) / Boundary) * Boundary`, `NewDeltaTime = NewAbs - QuantizedStartOfPrev`. Add property tests (`TE-09`) asserting every output delta lands on a `Boundary` multiple.

## API design & invariants

### 11. `midimsg:batch` and `midibin` batch are incompatible shapes  — **High**
**Location:** `src/midimsg.erl:104-106` vs. `src/midibin.erl:419-420,442-451`
**What's wrong:** `midimsg:batch/2` returns `{midi, {batch, [{id, UUID}, {messages, [Payload, …]}]}}` — a **proplist** whose message list holds *unwrapped* payloads (`{midi, Payload}` is stripped at `:105`). `midibin:encode({midi, {batch, Batch}})` calls `encode_batch/2`, which calls `encode/1` on each element of `Batch` and expects every element to be a `{midi, …}` tuple. Encoding `midimsg:batch(...)` output therefore runs `encode({id, UUID})`, which matches the final `encode(_)` clause (`:430-431`) → `ERR_NON_MIDI`, and short-circuits to `[{error, "non-MIDI message"}]`.
**Why it's wrong:** The seed set asked whether the two batch shapes are compatible; they are **not**. The `midibin` batch tests (`test/midibin_tests.erl:233-243`) use a list-of-`{midi,…}` shape that `midimsg:batch` never produces, so the suite gives false confidence. Cross-ref consumer report §C3.
**Fix:** pick one batch contract. Recommended: `midibin` should accept `{midi, {batch, Props}}` where `Props` carries metadata + `{messages, [...]}`, matching `midimsg:batch`; or `midimsg:batch` should emit `{midi, {batch, [{midi, P} || ...]}}`. Whichever is chosen, test the *actual* `midimsg:batch` output through `encode/1`.

### 12. Three incompatible message vocabularies under one "lingua franca" claim  — **High** (cross-cutting; home: consumer report §C2)
**Location:** `src/midimsg.erl:11-16` & `README.md:31` (the claim); `src/midifile.erl:98-348` (event tuples `{Name, DeltaTime, Values}`); `src/midimsg.erl` (`{midi, {Name, Data}}`); `src/midibin.erl` (codec terms).
**What's wrong:** `midimsg` wraps everything in `{midi, …}`; `midifile` events are bare `{name, DeltaTime, [values]}`; `midibin` only encodes a subset of the `midimsg` shapes. `midimsg:copyright/1` makes `{midi, {copyright, Text}}`, `midifile` emits `{copyright, DeltaTime, Data}`, and `midibin` has no clause for either. The header comment and README assert a single shared representation that does not exist.
**Why it's wrong:** Every `midimsg` meta constructor (copyright, lyric, marker, text, instrument, smpte, time_sig, keysig, …) is orphaned: `midibin:encode` rejects it (`ERR_MIDI_UNSUP`) and `midifile` expects a different tuple shape. This is the root cause behind several findings here and is consumer-critical — see consumer report §C2 for the full treatment and fix options.

### 13. Channel numbering differs across modules — 1-based in `midibin`, 0-based in `midifile`  — **Medium**
**Location:** `src/midibin.erl:16,169` (`Channel + 1` / `Channel - 1`) vs. `src/midifile.erl:98,111,123` (raw `Chan`, 0–15).
**What's wrong:** `midibin` presents channels to callers as 1–16; `midifile` event tuples expose the raw nibble 0–15. No code reconciles them.
**Why it's wrong:** A consumer that streams `midifile:read/1` output through the same path it uses for live `midibin`-decoded messages (the stated family design) will be off by one channel for every file event. There is no written invariant to say which convention is canonical. Cross-ref consumer report §C7.
**Fix:** choose one convention project-wide (1-based matches `midibin` and human numbering) and apply `+1` in `midifile` read / `-1` in write, or document the divergence loudly in both module headers.

### 14. `decode/1` and `encode/1` disagree on the failure representation  — **Medium**
**Location:** `src/midibin.erl:158-159` (`decode(Bin) -> {unknown, Bin}`) vs. `:428-431` (`encode` returns `{error, …}`).
**What's wrong:** Unrecognised input to `decode/1` yields `{unknown, Bin}`; unrecognised input to `encode/1` yields a tagged `{error, Reason}`. The two halves of the same codec use two different out-of-band conventions, neither matching the other.
**Why it's wrong:** A caller wrapping the codec cannot use one `case` arm for "codec couldn't handle this." `{unknown, Bin}` is not even an `{error, _}`, so it slips past error matching (`API-08`, `EH-01`, `DT-01`). Cross-ref consumer report §C4.
**Fix:** either make `decode/1` return `{error, {unknown, Bin}}`, or document `{unknown, Bin}` as a deliberate, distinct "well-formed but unsupported" channel and have `encode/1` mirror it. Decide and write it down.

## Error handling

### 15. `read/1` returns an untagged `{Path, Error}` on open failure  — **High**
**Location:** `src/midifile.erl:27-39` (the `Error -> {Path, Error}` arm at `:37-38`)
**What's wrong:** Success returns `{seq, …}`; failure returns `{Path, {error, Reason}}`. Neither is a `{ok, _}` / `{error, _}` pair.
**Why it's wrong:** Callers cannot pattern-match success vs. failure without knowing the bare tuple shapes; the failure tuple buries the real `file:open` reason one level deep behind the path (`EH-01`, `EH-12`, `API-08`). `midi` will call this on every file it streams and has nothing clean to branch on. Cross-ref consumer report §C4.
**Fix:** return `{ok, {seq, …}}` on success and `{error, {open, Path, Reason}}` on failure.

### 16. String error reasons resist matching  — **Medium**
**Location:** `include/errors.hrl:1-3`
**What's wrong:** `?ERR_NON_MIDI`, `?ERR_MIDI_UNSUP`, `?ERR_NOT_IMPL` are `{error, "non-MIDI message"}` etc. — the reason is a human string.
**Why it's wrong:** `EH-12` (structured, matchable reasons) and `AP-15` (no stringly-typed errors): callers must string-compare to distinguish causes, and any wording change silently breaks them. `midibin` returns these from `encode/1` and the batch path, so consumers inherit them.
**Fix:** use atoms with optional context — `{error, non_midi}`, `{error, {unsupported, Term}}`, `{error, not_implemented}` — and keep the human text in a `format_error/1`.

### 17. `exit/1` with a string is the library's error channel for oversized VLQs  — **High** (see also #5)
**Location:** `src/midifile.erl:381-382`
**What's wrong / why:** Beyond the `++` `badarg` (finding #5), using `exit/1` on a formatted string to report an expected, caller-fixable condition (a delta-time that doesn't fit in 28 bits) violates `EH-02`/`EH-03` (expected failures are values, exceptions are exceptional) and `EH-12`. A library should not unilaterally `exit`.
**Fix:** as in #5, raise a structured reason — or, better, return a tagged error up the `write/2` call chain so the caller decides.

## Concurrency / runtime safety

### 18. `midifile` keeps the running-status machine in the process dictionary  — **High**
**Location:** `src/midifile.erl:73-74, 96-97, 103-104, 109-110, 115-116, 121-122, 127-128, 133-134, 139-140, 145-146, 150-151, 195-196, 202-203, 210-211, 255-256, 288-289, 311, 320, 334, 352, 356, 359-361, 368-369`
**What's wrong:** `put(status, …)` / `put(chan, …)` and `get(status)` / `get(chan)` thread the running-status state through the *process dictionary* across nearly every read and write clause.
**Why it's wrong:** `PC-12` (avoid the process dictionary; thread state through the call) — this state is hidden, non-reentrant, and never cleaned up. Two `read/1`/`write/2` calls interleaved in one process (e.g. a server that reads one file while writing another, or any future parallelisation — note the `:57` "make this distributed" TODO) clobber each other's status/chan. It is also the chief reason `midifile` is hard to unit-test in isolation: every test would share and mutate global state. This is one of the two dominant root-cause clusters (see index trend note).
**Fix:** carry `{Status, Chan}` explicitly as accumulator arguments through `read_track`/`event_list`/`read_event` and through `track_io_list`/`event_io_list`/`running_status`, returning the updated pair alongside each event. Larger change, but it removes the whole class.

## Testing

### 19. Coverage is `midibin`-only; the defect-dense module has zero tests  — **High**
**Location:** `test/midibin_tests.erl` is the only test module; no tests for `midifile`, `midimsg`, `midiutil`.
**What's wrong:** `midifile` — which holds findings #1–#7 above, every one a Blocker or High — has no test at all, nor does `midimsg` (the batch-shape mismatch #11) or `midiutil` (the quantiser #10).
**Why it's wrong:** "It compiles and the tests pass" certifies only `midibin`'s round-trips. `TE-11` (test the public API) and `TE-09`/`TE-10` (property tests, coverage): the highest-risk surface — SMF read/write round-trips — is entirely unverified. The project even depends on PropEr (`rebar.config`) but ships no property tests.
**Fix:** add a `midifile_tests` suite that round-trips a known-good `.mid` fixture (read→write→read, byte-compare), plus a PropEr generator for event lists asserting `read(write(Seq)) =:= Seq`. That suite alone would have caught #1, #2, #3.

### 20. `sys_ex_test` and the batch tests bake in the bugs  — **Medium**
**Location:** `test/midibin_tests.erl:224-227` (sys_ex), `:233-243` (batch)
**What's wrong:** `sys_ex_test` asserts `{midi, {sys_ex, 123}}` — a single integer — codifying the single-byte limitation (#8) as the expected contract. The batch tests use `{midi, {batch, [{midi, …}, …]}}`, a shape `midimsg:batch` never emits (#11).
**Why it's wrong:** These tests actively defend the defects: fixing SysEx to accept binaries, or aligning the batch shapes, will "break" them, discouraging the fix (`TE-11`).
**Fix:** rewrite `sys_ex_test` around a multi-byte binary payload, and add a test that runs real `midimsg:batch(...)` output through `encode/1`.

## Performance

### 21. Quadratic accumulation in the batch codec  — **Low**
**Location:** `src/midibin.erl:439-440` (`decode_batch`: `Acc ++ [decode(Head)]`), `:447-450` (`encode_batch`: `Acc ++ [Encoded]`).
**What's wrong / why:** Building a result list with `Acc ++ [X]` per element is O(n²) (`FP-09`, `AP-09`): `++` copies the growing left operand each iteration. Batches are expected to be small today, hence Low, but the idiom is the canonical anti-pattern.
**Fix:** prepend and reverse — `decode_batch(Tail, [decode(Head) | Acc])` with a final `lists:reverse(Acc)`; likewise for `encode_batch`.

### 22. `look_for_chunk` scans one byte at a time  — **Low**
**Location:** `src/midifile.erl:44-49`
**What's wrong / why:** The chunk search advances a single byte per `file:pread`, acknowledged in its own comment. For well-formed files the cookie is at offset 0 so the cost is negligible, but a misaligned or padded file degrades to a per-byte syscall scan.
**Fix:** read a block and search in memory, or seek by the chunk length once `MThd` is parsed (chunk lengths are known).

## Idioms / style

### 23. Debug `io:format` left in the quantiser  — **Medium**
**Location:** `src/midiutil.erl:58`
**What's wrong / why:** `quantized_event/3` unconditionally prints `io:format("qe ~p, ~p, ~p~n", …)` on every event. `OPS-01` / `EH-14`: stray debug output in a library pollutes the caller's stdout and cannot be switched off. (Contrast `midifile`'s `?DPRINT` macro, which is at least compile-gated.)
**Fix:** delete it, or route through `logger` at debug level.

### 24. Dead module `midierrs`  — **Low**
**Location:** `src/midierrs.erl` (sole line `-module(midierrs).`)
**What's wrong / why:** An empty module with no exports and no code; nothing references it. `TL-04` (xref flags it) / `DC-11`. It is also newly untracked in git, suggesting an abandoned start on structured errors (which findings #16/#17 actually need).
**Fix:** either delete it, or make it the home for the structured `format_error/1` and error atoms that #16 calls for.

### 25. Sparse `-spec`, no `-moduledoc`/`-doc` anywhere  — **Medium**
**Location:** all modules. `midibin:encode/1`/`decode/1` have no `-spec`; `midifile:read/1`/`write/2` have none; `midimsg` specs are present but loose (`-spec keysig(...) -> tuple()`, `src/midimsg.erl:130`, and similar `-> tuple()` returns at `:121,146,165,174,183,202,...`) while many constructors (`copyright/1`, `lyric/1`, `text/1`, `batch/1,2`, `cc/3`, `note_on/2,3`) have none. No module carries `-moduledoc` and no function carries `-doc` (OTP-27 is available; `rebar.config` targets OTP 21–27).
**Why it's wrong:** `API-07`/`DT-16` (spec every export), `DC-01`/`DC-05` (module docs and purpose statements). The public codec — the surface the whole family calls — is undocumented and largely unspecced, so Dialyzer (`TL-01`, enabled in `rebar.config`) has little to check and consumers have no contract. `-> tuple()` is barely better than no spec.
**Fix:** add `-moduledoc` to each module, `-doc` + a precise `-spec` to every exported function (define `-type message()` / `-type event()` aliases and use them instead of `tuple()`).

### 26. `?DPRINT` no-op expands to a bare atom  — **Low**
**Location:** `src/midifile.erl:13` (`-define(DPRINT(X, Y), void).`)
**What's wrong / why:** With `DEBUG` off, every `?DPRINT(...)` expands to the atom `void` as a statement — harmless but a code smell, and it means the debug arguments are not even type-checked. `ID-14` (macros for constants, not control flow).
**Fix:** expand to `ok`, or gate the whole module on `logger` debug level rather than a macro.

## Cross-cutting findings

- **Root cluster A — the vocabulary split** (#11, #12, #13, #14): `midimsg`, `midifile`, and `midibin` each define a different message shape; the "lingua franca" claim is false; channel base and failure representation also diverge. This is the largest design debt and is treated end-to-end in the consumer-fit report.
- **Root cluster B — `midifile`'s process-dictionary state machine** (#18) underlies the module's untestability and is adjacent to the read/write asymmetries (#3, #4, #7) that a state-threaded, round-trip-tested rewrite would expose immediately.
- **Untested surface masks Blockers** (#19, #20): #1, #2, #3 are all fatal on the first real `.mid` round-trip and all invisible to the current suite.

## Things I looked for and did not find (clean checks)

1. **Running-status byte accounting in `midifile` read is correct.** The seed set claimed `:201-207` "mis-frames the 2-byte channel messages." Tracing it: the synthetic `<<Status:4, Chan:4, B0:8, B1:8>>` matches the 2-byte program/channel-pressure clauses (which ignore `B1` via `_:8` and return `2`), and the outer clause returns `NumBytes - 1`, i.e. `1` — exactly the one data byte a running-status program change occupies on the wire. For 3-byte events it returns `3 - 1 = 2`. The `-1` compensates correctly. **Refuted** as a byte-framing bug. (The real latent issue is narrower: `get(status)` is left at `0xFF`/`0xF0` after meta/SysEx rather than cleared per spec, so a running-status data byte following one of those would build a malformed status nibble — but spec-compliant files never emit running status there.)
2. **Pitch-bend byte order is correct** in both codecs — LSB then MSB (`midibin.erl:38-40,208`; `midifile.erl:137-141,306-308`). Matches the spec (spec report clean checks).
3. **`midibin` channel conversion is symmetric** — `Channel + 1` on every decode, `Channel - 1` on every encode; round-trip tests at `test/midibin_tests.erl:12-49` confirm channels 8 and 11 survive.
4. **`encode_batch/2` short-circuits on the first error** (`midibin.erl:446-449`) as the `e149ec9` commit intended, and the `batch_with_error_test` (`:245-255`) pins that behaviour.
5. **Clause ordering in `midibin:decode/1` is sound** (`FP-12`): the specific channel-mode clauses (controllers 120–127, `:46-81`) precede the generic CC clause (`:87-90`), and the `is_list/1` batch clause and `{error,_}` clause precede the `Bin` catch-all. No clause is shadowed or unreachable.
6. **`midibin:decode/1` is genuinely one-message-per-call** with no running-status expansion or stream reassembly — exactly the transport contract the consumer relies on (consumer report §R1 clean check).
7. **No `export_all`, no `-import`, no dynamic `M:F` calls** anywhere (`API-02`, `ID-12`, `ID-13`); all call sites are module-qualified and exports are explicitly listed per module.
